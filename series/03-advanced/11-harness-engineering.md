# Coding Agent 的 Harness 工程实践

> 原文作者：Kyle (HumanLayer) · 2026年3月12日
> 原文链接：https://www.humanlayer.dev/blog/skill-issue

## 核心观点

模型的失败不是模型的问题，而是**配置问题**。与其等待更强大的模型，不如专注于**充分利用当前的模型**。

```
coding agent = AI model(s) + harness
```

## 什么是 Harness Engineering？

Harness Engineering 是由 Viv (LangChain) 提出的概念，指的是通过配置点来定制和改进编码代理的输出质量和可靠性。它是 **Context Engineering** 的子集，而 Context Engineering 是"提示工程"的超集。

### 四大配置杠杆

1. **System Prompt** - 系统提示词
2. **Tools/MCPs** - 工具和 MCP 服务器
3. **Context** - 上下文管理
4. **Sub-agents** - 子代理

此外还有两个常被忽视的杠杆：
- **Hooks** - 自动化集成和确定性控制流
- **Skills** - 知识的渐进式披露

## 关键配置点

### 1. CLAUDE.md / AGENTS.md

ETH Zurich 的研究显示：
- LLM 生成的 agentfiles 反而会降低性能
- 人类编写的只有约 4% 的帮助
- 过多条件规则反而有害

**最佳实践**：
- 保持简洁（HumanLayer 的 CLAUDE.md 少于 60 行）
- 使用渐进式披露
- 避免无关上下文
- 包含具体的命令示例

### 2. MCP 服务器

**核心原则**：MCP 服务器主要用于扩展工具能力，而不是存储知识。

**注意事项**：
- 工具过多会导致"愚蠢区域"（dumb zone）
- 优先使用 CLI 而非 MCP（如 GitHub、Docker）
- 警惕提示注入风险

**最佳实践**：
- 只连接常用的 MCP 服务器
- 在 CLAUDE.md 中提供简洁的用法示例
- 定期清理不使用的工具

### 3. Skills

Skills 实现**渐进式披露**——代理只在需要时获取特定指令。

**使用场景**：
- 封装可复用的知识
- 封装工具和命令
- 按需加载特定领域的知识

**结构**：
```
skill-name/
├── SKILL.md           # 主文件，加载时注入
├── template.md        # 可选，模板文件
└── CLIs/              # 可选，包含的 CLI 工具
```

### 4. Sub-Agents

Sub-agents 是**最强大的配置杠杆**，主要用于：

#### 上下文控制（Context Firewall）
- 子代理的中间过程不会污染父代理的上下文
- 只有最终结果返回给父代理
- 避免"上下文腐化"（Context Rot）

#### 成本控制
- 父代理使用昂贵模型（如 Opus）
- 子代理使用便宜模型（如 Sonnet/Haiku）

**适用场景**：
- 代码库研究
- 定位特定定义或实现
- 追踪信息流
- 其他需要大量中间步骤的任务

### 5. Hooks

Hooks 在代理生命周期中的特定事件自动执行：

**常见用途**：
- **通知**：完成时播放声音
- **审批**：自动批准/拒绝某些工具调用
- **集成**：发送 Slack 消息、创建 PR
- **验证**：运行类型检查、格式化

**最佳实践**：
- 成功时静默退出
- 失败时返回详细错误
- 使用退出码 2 强制代理继续工作

## Back-Pressure（背压）机制

**核心洞察**：成功解决问题的概率与代理**自我验证能力**强相关。

### 验证机制

- 类型检查和构建步骤
- 单元测试/集成测试
- 代码覆盖率报告
- UI 交互测试（Playwright 等）

### 关键原则

验证机制必须**上下文高效**：
- 成功时静默， only 失败时返回详细输出
- 避免 4000 行测试输出淹没上下文
- 代理应该只看到错误，而不是通过的测试

## 实践经验总结

### 不推荐的做法

- 在遇到实际失败前就设计理想的配置
- "以防万一"安装大量技能和 MCP
- 每次结束后运行完整测试套件（5+ 分钟）
- 过度优化子代理的工具权限

### 推荐做法

- 从简单开始，只在代理实际失败时添加配置
- 设计、测试、迭代——丢弃无效的东西
- 通过仓库级配置分发最佳实践
- 优化迭代速度，而非"一次成功概率"
- 逐步精简暴露给模型的内容

## 总结

> 下次你的编码代理表现不及预期时，在责怪模型之前，先检查 harness。模型可能没问题，只是**技能问题**（skill issue）。
