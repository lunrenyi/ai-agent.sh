# Harness Engineering：利用 Codex 构建代理优先世界

> OpenAI 团队 5 个月构建百万行代码的实践经验总结

## 核心概述

本文来自 OpenAI 的 Ryan Lopopolo，讲述了一个大胆的实验：**构建一个 0 行手动代码的软件产品**。整个产品——应用逻辑、测试、CI 配置、文档、可观测性、内部工具——全部由 Codex AI 编写。团队估计这节省了约 10 倍的开发时间。

**关键数据**：
- 5 个月内构建约 **100 万行代码**
- 约 **1500 个 PR** 被合并
- 3 人团队 → 7 人团队
- 平均每人每天 **3.5 个 PR**
- 单次 Codex 运行可达 **6 小时**（通常在人类睡眠时）

---

## 核心理念：人类指导，代理执行

团队故意选择这个约束，目的是理解当软件工程团队的主要工作不再是写代码，而是**设计环境、表达意图、构建反馈循环**时，会发生什么。

> "Humans steer. Agents execute."

---

## 工程师角色的重新定义

### 从写代码到构建基础设施

由于没有人工编码，工程师的工作变成了不同类型的工程：专注于**系统、脚手架和杠杆效应**。

早期进展比预期慢，不是因为 Codex 无能，而是因为**环境描述不足**。代理缺乏取得进展所需的工具、抽象和内部结构。

### 深度优先的工作方式

当任务失败时，修复方法几乎从来不是"再试一次"。因为唯一的进步方式是让 Codex 工作，人类工程师会介入并问：
> "缺少什么能力？我们如何让它对代理既清晰又可执行？"

---

## 实践工作流

1. 人类通过 **Prompts** 与系统交互：描述任务 → 运行代理 → 允许它打开 PR
2. Codex 使用标准开发工具（gh、本地脚本、仓库嵌入的 skills）自行收集上下文
3. 人类可以审查 PR，但不是必须的——**代理对代理的审查**已成为主流

---

## 增加应用可读性

随着代码吞吐量增加，瓶颈变成了**人工 QA 能力**。团队通过让应用 UI、日志、指标本身对 Codex 可读来解决这个问题。

### Chrome DevTools Protocol 集成

- 应用可在每个 git worktree 上启动
- 代理可以用 DOM 快照、截图、导航来驱动
- 可以**复现 bug、验证修复、推理 UI 行为**

### 可观测性栈

- 日志、指标、追踪通过本地可观测性栈暴露
- Codex 可以使用 **LogQL、PromQL、TraceQL** 查询
- 提示如"确保服务启动在 800ms 内完成"变得可操作

---

## 知识管理：把仓库作为系统记录

### 大型 AGENTS.md 失败的原因

1. **上下文是稀缺资源**：巨型指令文件挤占了任务、代码和相关文档
2. **过多指导变成无指导**：当一切都是"重要"时，就没有了优先级
3. **快速腐化**：单一手册变成过时规则的墓地
4. **难以验证**：单一文件不容易进行机械检查

### 解决方案：把 AGENTS.md 变成目录

- 短的 AGENTS.md（约 100 行）作为**地图**，指向更深层的真相来源
- 知识库存在于结构化的 `docs/` 目录
- 计划被视为一等公民：临时轻量计划用于小改动，复杂工作使用执行计划

### 机械执行

- 专用 linters 和 CI 任务验证知识库是最新的、正确交叉链接的
- 定期的"文档园丁"代理扫描过时文档并打开修复 PR

---

## 代理可读性是目标

由于仓库完全是代理生成的，它首先为 Codex 的可读性进行了优化。

> 从代理的角度来看，任何在运行时无法在上下文中访问的东西都**不存在**。

知识如果存在于 Google Docs、聊天记录或人们的头脑中，对系统来说就是不可访问的。

### 技术选择

- 团队倾向于依赖可以被完全内化和推理的仓库本地技术
- **"无聊的"技术**更容易被代理建模（可组合性、API 稳定性、训练数据存在）
- 在某些情况下，让代理重新实现功能子集比处理不透明的上游行为更便宜

---

## 强制执行架构和品味

### 分层领域架构

团队在应用周围构建了严格的架构模型：
- 每个业务域分为固定的**层集**
- 严格验证依赖方向和允许的边
- 自定义 linters 和结构测试强制执行这些约束

```
Types → Config → Repo → Service → Runtime → UI
```

跨领域关注点（auth、connectors、telemetry、feature flags）通过单一显式接口进入：**Providers**

> 这是通常等到有数百名工程师时才推迟的架构。使用编码代理，它是**早期先决条件**：约束是允许速度而不衰退或架构漂移的方式。

### 品味不变量

- 结构化日志静态强制
- 模式和类型命名约定
- 文件大小限制
- 平台特定可靠性要求

---

## 吞吐量改变合并理念

在 Codex 吞吐量增加的情况下，许多传统工程规范变得**适得其反**：

- 最小阻塞合并门
- PR 短生命周期
- 测试flake通常用后续运行解决，而不是无限阻塞

> 在代理吞吐量远超过人类注意力的系统中，修正很便宜，等待很昂贵。

---

## 代理生成的实际含义

当团队说代码库由 Codex 代理生成时，意思是**一切**：

- 产品代码和测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估工具
- 审查评论和响应
- 管理仓库本身的脚本
- 生产仪表板定义文件

---

## 增加自主性水平

随着更多开发循环被编码到系统中——测试、验证、审查、反馈处理、恢复——仓库最近跨越了一个有意义的阈值：**Codex 可以端到端驱动新功能**。

给定单个提示，代理现在可以：

1. 验证代码库当前状态
2. 复现报告的 bug
3. 录制展示失败的视频
4. 实现修复
5. 通过驱动应用验证修复
6. 录制展示解决方案的第二个视频
7. 打开 PR
8. 响应代理和人类反馈
9. 检测并修复构建失败
10. 仅在需要判断时升级到人类
11. 合并更改

---

## 熵和垃圾回收

完全代理自主也引入了新问题。Codex 复制仓库中已经存在的模式——即使是不均匀或次优的。随着时间推移，这不可避免地导致漂移。

### 解决方案：Golden Principles

团队编码了称为"黄金原则"的内容到仓库中，并构建了定期清理流程：

1. 优先使用共享工具包而不是手写助手
2. 不 YOLO 式探测数据——验证边界或依赖类型化 SDK

定期后台 Codex 任务扫描偏差、更新质量评分、打开有针对性的重构 PR。大多数可以在**一分钟内**审查并自动合并。

> 技术债务就像高利贷：几乎总是持续小还比让它复合然后痛苦地一次性还清更好。

---

## 关键经验总结

| 主题 | 核心要点 |
|------|----------|
| **角色转变** | 工程师从写代码 → 设计环境、表达意图、构建反馈循环 |
| **知识管理** | AGENTS.md 是目录，不是手册；知识必须在仓库内 |
| **架构** | 严格边界 + 可预测结构 = 代理效率；约束是速度的基础 |
| **品味** | 人味通过规则持续强制，而不是一次性审查 |
| **合并理念** | 代理吞吐量 >> 人类注意力时，等待是最贵的 |
| **垃圾回收** | 技术债务持续小还 >> 痛苦的大还 |

---

## 未来挑战

- **架构一致性**：完全代理生成的系统，架构连贯性如何多年演变？
- **人类判断**：人类判断在哪里增加最大杠杆，如何编码它让它复合？
- **模型进化**：随着模型变得更强大，系统将如何演变？

> "构建软件仍然需要 discipline，但它更多出现在脚手架中，而不是代码中。"
