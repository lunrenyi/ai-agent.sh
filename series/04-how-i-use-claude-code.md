# 我是如何使用 Claude Code

> 翻译整理自 Boris Tone 的博客

---

## 核心原则

> **永远不要让 Claude 写代码，直到你审查并批准了书面计划。**

这种将**规划与执行分离**的方式是作者认为最重要的事情。

---

## 工作流程总览

```
研究 → 规划 → 注解循环 → 实现 → 反馈
```

---

## 阶段一：研究

每个有意义的任务都从**深度阅读指令**开始。要求 Claude 在做任何事情之前彻底理解代码库的相关部分，并且必须将发现写入持久化的 markdown 文件。

### 研究指令示例

```
"深入阅读这个文件夹，深刻理解它的工作原理、功能和所有特性。
完成后，将你的学习和发现写成详细报告，写入 research.md"

"详细研究通知系统，理解其复杂性，写一份详细的 research.md 文档"

"研究任务调度流程，深刻理解它，并寻找潜在的 bug。
一直研究直到找到所有 bug。完成后，将发现写入 research.md"
```

### 关键要点

| 要点 | 说明 |
|------|------|
| 使用强语气词 | 使用 "deeply"、"in great details"、"intricacies" 等词汇，否则 Claude 会 skim |
| 书面产物是关键 | research.md 是审查表面 |
| 研究错误 → 计划错误 → 实现错误 | 最大的失败模式不是语法错误，而是实现孤立看起来工作但破坏周围系统 |

---

## 阶段二：规划

审查研究后，请求详细的实现计划，放在单独的 markdown 文件中。

### 规划指令示例

```
"我想构建一个新功能 <名称和描述>，扩展系统来实现 <业务结果>。
写一份详细的 plan.md 文档，列出如何实现，包括代码片段"

"列表端点应该支持基于游标的分页而不是偏移。
写一份详细的 plan.md。在提出更改之前先阅读源文件，基于实际代码库制定计划"
```

### 计划内容

- 方法的详细解释
- 显示实际更改的代码片段
- 将被修改的文件路径
- 注意事项和权衡

### 小技巧

对于封装良好的功能，可以分享开源项目中的好的实现作为参考：

> "这是他们做可排序 ID 的方式，写一个 plan.md 解释我们如何采用类似方法"

---

## 注解循环（核心创新）

这是工作流程中最独特的部分，也是作者添加最多价值的部分。

```
Claude 写 plan.md → 我在编辑器中审查 → 我添加内联注释 →
发送 Claude 回去更新文档 → 重复 1-6 次 → 满足后请求待办事项列表
```

### 如何添加注释

在计划中直接添加**内联注释**，纠正假设、拒绝方法、添加约束或提供 Claude 不知道的领域知识。

### 真实注释示例

| 类型 | 示例 |
|------|------|
| 技术纠正 | "使用 drizzle:generate 进行迁移，而不是原始 SQL" |
| API 纠正 | "不——这应该是 PATCH，不是 PUT" |
| 功能删除 | "完全删除这部分，我们不需要缓存" |
| 简化 | "队列消费者已经处理重试，所以这个重试逻辑是多余的，删除它" |
| 逻辑纠正 | "这是错误的，可见性字段需要在列表本身而不是单个项目上" |

### 关键命令

> "我在文档中添加了一些注释，解决所有注释并相应更新文档。**先不要实现**"

> [!IMPORTANT]
> **"不要实现 yet" 这个明确的守卫至关重要。** 没有它，Claude 会在认为计划足够好时就跳到代码。

### 为什么效果这么好

- markdown 文件充当**共享可变状态**
- 可以按照自己的节奏思考
- 精确地标注问题所在，而不需要在聊天消息中解释一切

### 待办事项列表

在实现开始之前，总是请求粒度的任务分解：

> "在计划中添加详细的待办事项列表，列出完成计划所需的所有阶段和个别任务。**先不要实现**"

---

## 阶段三：实现

当计划准备好后，发出实现命令。

### 标准实现提示

> "全部实现。当任务或阶段完成时，在计划文档中将其标记为完成。
> 不要停止，直到所有任务和阶段都完成。
> 不要添加不必要的注释或 jsdocs，不要使用 any 或 unknown 类型。
> 持续运行类型检查以确保你没有引入新问题。"

### 这个命令编码的内容

| 指令 | 含义 |
|------|------|
| "全部实现" | 做计划中的所有事情，不要挑挑拣拣 |
| "在计划文档中标记为完成" | 计划是进度的真实来源 |
| "不要停止直到所有任务完成" | 不要中途停下来确认 |
| "不要添加不必要的注释或 jsdocs" | 保持代码简洁 |
| "不要使用 any 或 unknown 类型" | 保持严格类型 |
| "持续运行类型检查" | 尽早发现问题，不要等到最后 |

### 核心理念

**希望实现是无聊的。** 创意工作发生在注解循环中。一旦计划正确，执行就应该 straightforward。

---

## 实现过程中的反馈

一旦 Claude 正在执行计划，作者的角色从**架构师转变为监督者**。提示变得更加简短。

### 规划注释可能是一段话，实现修正通常是一句话

- "你没有实现 `deduplicateByTitle` 函数。"
- "你在主应用中构建了设置页面，但它应该在管理应用中，移动它。"
- "更宽"
- "仍然被裁剪了"
- "有 2px 间隙"

### 对于视觉问题

有时会**附加截图**。一张错位表格的截图比描述问题更快。

### 引用现有代码

> "这个表应该和 users 表完全一样，相同的表头、相同的分页、相同的行密度。"

### 当事情走向错误方向

不尝试修补，而是**回滚并重新调整范围**：

> "我回滚了一切。现在我只想让列表视图更简洁——没有别的。"

---

## 保持在驾驶座上

即使将执行委托给 Claude，**永远不会给它对构建什么的完全自主权**。绝大多数主动引导都在 `plan.md` 文档中完成。

### 评估每个项目

| 操作 | 说明 |
|------|------|
| **接受原样** | 计划看起来不错 |
| **修改方法** | 改变实现方式 |
| **跳过/删除** | 移除某些功能 |
| **覆盖技术选择** | 指定具体技术 |

### 示例

- "第一个，只要使用 Promise.all，不要把它弄得太复杂；第三个，提取到一个单独的函数中以提高可读性；忽略第四个和第五个，它们不值得复杂性。"
- "从计划中删除下载功能，我现在不想实现这个。"
- "这三个函数的签名不应该改变，调用者应该适应，而不是库。"
- "使用这个模型而不是那个" 或 "使用这个库的内置方法而不是写一个自定义的。"

## 单个长会话

作者在**单个长会话**中运行研究、规划和实施，而不是将它们分开。

### 实际表现

作者没有看到每个人都谈论的 50% 上下文窗口后的性能降解。实际上，当说"全部实现"时，Claude 整个会话都在建立理解：
- 在研究期间阅读文件
- 在注解循环期间完善其心智模型
- 吸收作者的领域知识纠正

### 持久产物

计划文档在压缩中完整保留。可以随时指向它。

---

## 一句话总结

> **深度阅读，写一个计划，注解计划直到正确，然后让 Claude 全部执行，一路检查类型。**

---

## 核心理念

这个工作流程的核心是**将思考与打字分离的严格管道**：

| 阶段 | 防止的错误 |
|------|-----------|
| 研究 | 无知的更改 |
| 规划 | 错误的更改 |
| 注解循环 | 判断失误 |
| 实现 | 执行偏差 |
