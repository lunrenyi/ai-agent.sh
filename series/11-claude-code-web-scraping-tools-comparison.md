# Claude Code 网页抓取方案深度对比：从 WebFetch 到 Agent-Reach

> 用 Claude Code 做内容创作，抓取网页是刚需。本文实测对比 5 种方案，帮你找到最合适的工具。

## 核心观点：它们不在同一个层次

这 5 种方案最容易踩的坑，是直接横向比较。它们其实是不同技术层次的东西——互补关系，不是替代关系。

| 层级 | 方案 | 定位 |
|------|------|------|
| 网络层 | WebFetch | 最轻量的 HTTP 请求工具 |
| 浏览器层 | Playwright MCP | 模拟真人操作的真实浏览器 |
| 爬虫框架层 | Scrapling | 自适应解析的 Python 爬虫框架 |
| 云端服务层 | Firecrawl | 网页数据提取的 SaaS 服务 |
| 聚合编排层 | Agent-Reach | 11+ 社交平台的统一接入层 |

## 方案一：WebFetch

**定位**：Claude Code 内置工具，零配置，开箱即用

### 工作方式
发 HTTP 请求 → 拿 HTML → 转 Markdown 返回

### 优点
- 轻量：零依赖、零配置
- 安全：内置沙箱、自动 HTTPS 升级、15 分钟缓存

### 缺点
- **不执行 JavaScript**
- 现代网页大量依赖 JS 渲染，WebFetch 拿到可能只是空壳
- 不支持登录，不能点击、滚动、填表单
- 碰到企业级反爬策略可能被直接拦截

> 简单说，WebFetch 拿到的是「服务器返回的原始文档」，不是「你在浏览器里看到的页面」

### 适用场景
- 快速看一个博客文章
- 抓公开的 API 文档
- 获取静态页面文本

### 不适用场景
- X/Twitter
- SPA 单页应用
- 任何需要登录的页面

### 实测结果
用它抓 X 帖子，直接返回 `JavaScript is not available`，完全拿不到内容。

---

## 方案二：Playwright MCP

**定位**：微软维护的浏览器自动化框架，通过 MCP 协议接入 Claude Code

### 工作方式
启动真实 Chromium 浏览器 → 完整加载页面 → 执行 JS → 渲染 DOM

### 优点
- 拿到的是「你眼睛看到的那个页面」
- JS 渲染的内容、动态加载的数据，全都有
- 能交互：点按钮、填表单、模拟滚动、截图
- 可以在浏览器里走完登录流程
- 微软维护，社区成熟，文档丰富
- 数据全部本地处理

### 缺点
- 重：每次操作都启动完整 Chromium，资源消耗不小
- 一次只能操作一个页面
- 本质是测试/自动化工具，不是为批量爬取设计

### 适用场景
- JS 渲染页面（SPA、React/Vue 应用）
- 需要登录的内容
- 需要交互操作
- 截图

### 不适用场景
- 大规模批量爬取
- 高频率抓取

### 实测结果
同样抓 X 帖子，完整拿到：全文、作者信息、互动数据（回复/转发/点赞/书签/浏览量）、图片链接。未登录状态就能抓取 Article 类型帖子。

## 方案三：Scrapling

**定位**：Python 爬虫框架，GitHub 20.6K stars，92% 测试覆盖率

### 工作方式
提供三种 Fetcher 模式可切换：
- `Fetcher`：普通 HTTP 请求（类似 WebFetch）
- `StealthyFetcher`：反反爬模式，内置绕过 Cloudflare
- `DynamicFetcher`：浏览器渲染（类似 Playwright）

### 核心特性：自适应解析
做过爬虫的都知道，网站一改版，选择器就失效，得手动更新。Scrapling 用**相似度算法**自动重新定位元素，DOM 结构变了也能找到对应内容。

### 性能
官方数据：解析速度比 BeautifulSoup **快 400-600 倍**

v0.4 还引入 Spider 框架，类 Scrapy API，支持：
- 异步并发
- 断点续爬
- 流式处理

### 缺点
- 门槛高：需要 Python 3.10+ 环境
- 学习曲线比前两个陡
- 不适合交互场景

### 适用场景
- 批量提取结构化数据
- 网站有 Cloudflare 防护
- 长期监控网站变化

### 不适用场景
- 偶尔抓一个页面（杀鸡用牛刀）

---

## 方案四：Firecrawl

**定位**：云端 SaaS，YC 孵化，$14.5M A 轮，GitHub 69K+ stars

### 工作方式
给一个 URL → 云端完成所有脏活（浏览器渲染、反爬绕过、内容清洗、结构化提取）→ 返回干净的 Markdown 或结构化 JSON

### 额外能力
- 全站爬取
- 站点地图发现
- 搜索+抓取一体化
- 2026 年 1 月推出 `/agent` 功能：智能导航复杂网站

### 优点
- **省心**：不用装本地依赖，不用管版本兼容
- 官方 MCP Server，`npx -y firecrawl-mcp` 一行搞定

### 缺点
- **隐私问题**：所有内容经过 Firecrawl 服务器
- 费用：免费额度有限，大量使用需付费
- 服务商依赖：Firecrawl 挂了你就挂了

### 适用场景
- 大规模全站爬取
- 不想维护工具链

### 不适用场景
- 涉及敏感数据（商业敏感信息、用户数据）

---

## 方案五：Agent-Reach

**定位**：脚手架/聚合编排层，GitHub 4.2K stars

### 工作方式
把 11+ 平台的最佳抓取工具整合在一起，通过 MCP 提供统一入口：
- YouTube → yt-dlp（148K stars）
- X → xreach CLI（cookie 认证）
- 通用网页 → Jina Reader
- 还有 B 站、小红书、Reddit、LinkedIn 等

### 优点
- **广度**：需要同时从多个社交平台采集时能省不少事
- 本地运行，免费开源

### 缺点
- 依赖链太长：底层挂着 yt-dlp、xreach、Jina Reader 等一堆工具
- 项目较新（v1.2.0），稳定性还在验证中
- 多工具版本兼容的维护成本不低

### 适用场景
- 跨多个社交平台采集
- YouTube、B 站、小红书等多平台同时抓取

## 选型建议

按场景选，别纠结「哪个最好」：

| 场景 | 推荐方案 |
|------|----------|
| 快速看一个静态页面 | WebFetch |
| 页面需要 JS 渲染或登录 | Playwright MCP |
| 需要点击、填表等交互 | Playwright MCP |
| 批量提取结构化数据 | Scrapling |
| 网站有 Cloudflare 防护 | Scrapling StealthyFetcher |
| 长期监控网站变化 | Scrapling |
| 大规模全站爬取 | Firecrawl |
| 跨多个社交平台采集 | Agent-Reach |
| 在意数据隐私 | Scrapling / Agent-Reach |
| 不想维护工具链 | Firecrawl |

## 我在用的组合

### 日常组合：WebFetch + Playwright MCP
大部分场景用 WebFetch 先试，静态页面直接搞定。遇到 JS 渲染或需要交互的再切 Playwright。**覆盖 80% 日常需求**。

### 进阶组合：加上 Scrapling MCP
有批量采集或长期监控需求时，Scrapling 的批量调度和自适应解析是前两个做不到的。三者都本地运行，数据不外传。

### 全覆盖组合：再加 Agent-Reach
需要同时从 YouTube、B 站、小红书等多平台采集。但要有心理准备，依赖链长，维护成本也高。

---

## 几个容易忽略的点

1. **WebFetch 不等于浏览器**：很多人第一次用会困惑「为什么拿不到内容」，原因就是它不执行 JS。现在大部分网站都有 JS 渲染内容，适用范围比想象的窄。

2. **Playwright 不适合批量**：它启动完整 Chromium，一次操作一个页面。拿它做批量爬虫，就像开法拉利送外卖。

3. **Firecrawl 的隐私问题不能忽视**：所有数据经过第三方服务器处理。公开文章问题不大，但涉及商业敏感信息或用户数据，请选本地方案。

4. **Agent-Reach 本质是编排层**：它自己不做抓取，底层全靠第三方工具。升级某个依赖可能引发连锁问题。

---

## 结论

这 5 种方案各自擅长不同层次的问题，没有「最好」的方案，只有「最合适」的方案。

**我的建议**：先从 WebFetch 开始，不够用了上 Playwright，有批量需求再上 Scrapling。按需升级，别过度配置。
