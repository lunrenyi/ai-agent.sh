# Claude Code Agent Teams 完整指南

> 多智能体协作实战手册

---

## 概述

Agent Teams 是 Claude Code 的**实验性功能**，用于协调多个 Claude 实例在同一个项目中协同工作。与单智能体串行模式不同，它引入了真正的协作机制：多个 AI 可以并行工作、互相通信、共享任务进度，甚至通过「对抗式讨论」验证判断。

Agent Teams 与 [Subagents](/docs/en/sub-agents) 不同：Subagents 在单个会话中运行，只能向主智能体汇报结果；而 Agent Teams 中的每个队友都是独立的 Claude 实例，可以直接相互通信、协调工作。

> **注意**：Agent Teams 当前存在一些[已知限制](#限制说明)，包括会话恢复、任务协调和关闭行为等方面。

---

## 核心组件

### Team Lead（团队负责人）

团队的主会话，负责：
- 生成队友
- 分配任务
- 协调工作
- 汇总结果

可设置为仅负责协调（不直接写代码）。

### Teammates（队友智能体）

各自独立执行任务的智能体：
- 有独立的上下文窗口
- 加载项目相关信息（CLAUDE.md、MCP 服务、技能）
- 可以直接与其他队友通信

### Task List（共享任务列表）

- 三种状态：pending、in progress、completed
- 支持任务依赖，未解决依赖的任务无法被认领
- 使用文件锁机制防止竞争

### Mailbox（消息系统）

队友之间的通信机制：
- `message`：向指定队友发送消息
- `broadcast`：向所有队友广播（成本随规模增长）

### 架构细节

团队配置和任务列表本地存储：
- **团队配置**：`~/.claude/teams/{team-name}/config.json`
- **任务列表**：`~/.claude/tasks/{team-name}/`

团队配置包含 `members` 数组，记录每个队友的名称、agent ID 和类型。队友可以读取此文件来发现其他团队成员。

## Agent Teams vs Subagents

| 特性 | Subagents | Agent Teams |
|------|-----------|-------------|
| 上下文 | 独立窗口，结果返回主智能体 | 独立窗口，完全自主 |
| 通信 | 仅向主智能体汇报 | 队友之间直接通信 |
| 协调 | 主智能体统一管理 | 共享任务列表，自主协调 |
| 适用场景 | 专注任务，只需结果 | 复杂任务，需要讨论协作 |
| Token 成本 | 较低 | 较高 |

**选型建议**：
- 快速明确产出 → Subagents
- 复杂需协作 → Agent Teams

## 快速设置指南

### 步骤 1：启用实验性标志

```bash
nano ~/.claude/settings.json
```

添加配置：

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

### 步骤 2：选择显示模式

| 模式 | 说明 |
|------|------|
| in-process | 所有队友运行在同一终端，用 Shift+Up/Down 切换 |
| tmux | 分屏模式，每个队友独立窗格，需要 tmux 或 iTerm2 |

默认 auto：检测到 tmux 时自动使用分屏模式。

```json
{
  "teammateMode": "in-process"
}
```

或启动时覆盖：

```bash
claude --teammate-mode in-process
claude --teammate-mode tmux
```

**iTerm2 分屏设置**：
1. 安装 [`it2` CLI](https://github.com/mkusaka/it2)
2. 在 iTerm2 中启用 Python API：**iTerm2 → Settings → General → Magic → Enable Python API**

### 步骤 3：安装 tmux（如需分屏）

```bash
# Mac
brew install tmux

# Ubuntu/Debian/WSL
sudo apt update && sudo apt install tmux
```

> tmux 在某些操作系统上有已知限制。在 iTerm2 中使用 `tmux -CC` 是推荐的方式。

### 步骤 4：验证启用

重启 Claude Code，运行 `/config` 查看配置列表。

## 创建团队

### 简单方式

```
创建一个智能体团队来重构认证模块。
将工作分解为可以独立完成的并行任务。
```

### 手动指定

```
创建一个包含 3 个队友的团队：
- 一个重构登录流程
- 一个重构注册流程
- 一个为两者更新测试

每个队友使用 Sonnet 模型。
```

### 指定模型

```
创建一个包含 4 个队友的团队：
- 一个使用 Haiku 的研究员，用于快速查找信息
- 一个使用 Opus 的架构师，用于复杂设计决策
- 两个使用 Sonnet 的实现者，用于实际代码更改
```

## 导航与交互

### In-Process 模式

| 操作 | 快捷键 |
|------|--------|
| 切换队友 | Shift+Up / Shift+Down |
| 进入队友视图 | Enter |
| 回到 Lead | Escape |
| 打断队友 | Escape |

- 点击窗格选择队友
- 在对应分屏中输入指令
- 执行 /tasks 查看任务列表

## 高级控制

### 委托模式

Team Lead 只负责指挥，不改代码：

1. 启动团队
2. 按 Shift+Tab 切换

### 计划批准机制

队友动手前先提交规划：

```
创建一个架构师队友来重构数据库架构。
在它们进行任何更改之前要求计划批准。
```

当队友完成规划后，会向 Lead 发送计划批准请求。Lead 审查计划后可以批准或拒绝并反馈。如果被拒绝，队友保持在规划模式，根据反馈修改后重新提交。批准后，队友退出规划模式开始实施。

**影响 Lead 判断**：可以在 prompt 中给出标准，如"只批准包含测试覆盖的计划"或"拒绝修改数据库模式的计划"。

### 预批准权限

```
/permissions
```

提前批准常用操作，避免频繁请求。队友继承 Lead 的权限设置。如果 Lead 使用 `--dangerously-skip-permissions`，所有队友也会跳过权限检查。

### 关闭队友

```
请关闭队友 researcher
```

Lead 发送关闭请求。队友可以批准并优雅退出，也可以拒绝并解释原因。

### 清理团队

```
清理团队
```

需要先关闭所有队友。Lead 会检查是否有活跃的队友，如有则清理失败。

> 始终使用 Lead 来清理团队。队友不应运行清理，因为它们的团队上下文可能无法正确解析，可能导致资源处于不一致状态。

### 质量门控（Hooks）

使用 [hooks](/docs/en/hooks) 在队友完成工作或任务完成时强制执行规则：

- [`TeammateIdle`](/docs/en/hooks#teammateidle)：队友即将空闲时运行。退出码 2 发送反馈并让队友继续工作
- [`TaskCompleted`](/docs/en/hooks#taskcompleted)：任务标记完成时运行。退出码 2 阻止完成并发送反馈

## 实战应用场景

### 场景 1：并行代码审查

```
创建一个智能体团队来审查 PR #142，生成三个审查员：
- 安全专家：检查漏洞、注入风险、认证缺陷
- 性能分析师：查找瓶颈、N+1 查询、内存问题
- 测试验证者：检查边缘情况和测试覆盖率
```

每个审查员从同一个 PR 出发，但应用不同的过滤条件。Lead 在他们完成后综合三个审查员的发现。

### 场景 2：对抗式调试

```
用户报告结账端点间歇性 500 错误，大约 5% 的请求失败。

创建 5 个队友调查不同可能原因：
1. 数据库连接池在高负载下耗尽
2. 库存预留中的竞态条件
3. 第三方支付 API 超时处理
4. 内存压力导致垃圾回收暂停
5. 服务间网络问题

让队友相互挑战、反驳彼此的理论。
```

**对抗式讨论的关键**：单一智能体往往找到一个看似合理的解释后就停止搜索。通过让多个独立调查者互相尝试反驳对方，存活下来的理论更可能是真正的根本原因。

### 场景 3：跨层功能开发

```
创建一个智能体团队来开发通知系统：
- 队友 1：后端 API
- 队友 2：数据库表结构和迁移
- 队友 3：前端 React 组件
- 队友 4：实时更新的 WebSocket 集成
- 队友 5：端到端集成测试
```

## 最佳实践

### 适合场景

- 并行推进能明显提高效率
- 各个队友可在相对独立范围工作
- 调研、代码审查、新功能拆分开发
- 需要队友之间直接讨论、对齐结论

### 不适合场景

- 任务本身是严格顺序的，无法并行
- 多个队友需要频繁修改同一个文件
- 工作之间强依赖，容易相互等待
- 体量很小的日常任务，协调成本高于收益

### 团队规模建议

- **推荐范围**：3-5 个队友
- 每个队友 5-6 个任务，保持高效产出
- 15 个独立任务 → 3 个队友是不错的起点
- Token 成本随数量线性增长
- 协调开销随人数增加

**原则**：三个专注的队友往往胜过五个分散的队友。

### 任务粒度建议

- **过小**：协调开销超过收益
- **过大**：队友长时间工作无检查点，返工风险高
- **适中**：自包含单元，产生明确产出（如一个函数、一个测试文件、一次审查）

### 注意事项

1. **Token 成本**：每个队友是独立实例，成本随数量线性增长
2. **任务粒度**：过小协调成本高，过大返工风险高
3. **文件隔离**：避免多人修改同一文件
4. **持续关注**：定期查看进度，及时调整策略
5. **给队友足够上下文**：队友加载项目上下文（CLAUDE.md、MCP 服务、技能），但不继承 Lead 的对话历史。在生成 prompt 中包含任务特定细节

## 故障排除

### 队友不显示

- In-process 模式下可能已在运行但不可见，按 Shift+Down 循环查看
- 检查任务是否足够复杂，值得创建团队
- 如果请求分屏模式，确保 tmux 已安装且在 PATH 中：`which tmux`
- 对于 iTerm2，验证 `it2` CLI 已安装且 Python API 已启用

### 权限请求过多

队友权限请求会汇总到 Lead，可能造成干扰。在生成队友前在权限设置中预批准常用操作。

### 队友遇到错误后停止

检查队友输出（In-process 模式用 Shift+Down，分屏模式点击窗格），然后：
- 直接给出额外指令
- 生成替换队友继续工作

### Lead 过早关闭

Lead 可能认为团队已完成，但实际任务尚未完成。告诉它继续。如果它开始自己实现而不是委托，告诉它等待队友完成任务后再继续。

### tmux 会话残留

如果团队结束后 tmux 会话仍然存在，可能未完全清理。列出并杀死：

```bash
tmux ls
tmux kill-session -t <session-name>
```

## 限制说明

Agent Teams 是实验性功能，当前限制包括：

- **不支持会话恢复**：/resume 和 /rewind 不会恢复 in-process 队友。恢复后 Lead 可能尝试联系已不存在的队友
- **任务状态可能不同步**：队友有时未能将任务标记为完成，阻止依赖任务。如果任务卡住，检查工作是否实际完成，手动更新任务状态或让 Lead 提醒队友
- **关闭可能较慢**：队友在关闭前完成当前请求或工具调用，可能需要时间
- **单会话单团队**：Lead 只能同时管理一个团队。开始新团队前先清理当前团队
- **不支持嵌套团队**：队友不能生成自己的团队或队友。只有 Lead 可以管理团队
- **Lead 固定**：创建团队的会话在其生命周期内是 Lead。不能将队友晋升为 Lead 或转移领导权
- **权限在生成时设置**：所有队友从 Lead 的权限模式开始。生成后可以更改个别队友模式，但生成时不能设置每队友模式
- **分屏需要 tmux 或 iTerm2**：默认 in-process 模式在任何终端都能工作。VS Code 集成终端、Windows Terminal 或 Ghostty 不支持分屏模式

## 总结

Agent Teams 是当前自然语言多智能体编排中较为优雅的实现。它与 Claude Code 生态深度结合，引入了声明式的团队协作机制。适用于复杂多模块开发、多角度调研或需要并行推进的场景。
