# 编程 Agent 如何重塑工程、产品和设计

> 原文作者：Harrison Chase (LangChain CEO)
> 原文链接：https://x.com/hwchase17/status/2031051115169808685

## 核心观点

软件公司的 EPD（工程、产品、设计）存在的意义就是做出好软件。编程 Agent 突然让写代码变得异常简单，EPD 的角色定位正在发生根本性变化。

## 流程变革

### PRD 已死

传统的软件开发流程：
```
PRD → 设计稿 → 代码
```

写软件需要大量时间和精力，所以有了专门的分工。PRD 是核心枢纽，把整个流程串起来。

**编程 Agent 颠覆了这一切**——它能把一个想法直接变成可运行的软件。传统的"从 PRD 开始"的开发方式终结了。

### 瓶颈从实现转向评审

现在谁都能写代码，意味着谁都能把东西做出来。但这不代表做出来的东西：
- 架构合理
- 解决了正确的问题
- 好用

EPD 的角色变成了**评审者**，确保代码"足够好"：
- **工程视角**：架构是否可扩展、高性能、健壮？
- **产品视角**：是否解决了用户痛点？
- **设计视角**：界面是否易用、直观？

### PRD 万岁

PRD **文档形式**死了，但描述产品需求的**文字本身**活得好好的。

评审时需要知道：代码里某个地方是有意为之还是偶然写成？这就需要传达**意图**。

> 未来的 PRD 可能就是结构化、带版本管理的 prompt。

## 角色影响

### 通才比以往更有价值

**通才**：在产品、工程和设计三方面都有不错感觉的人。

- 过去：实现是瓶颈，通才也得和别人沟通才能做完
- 现在：只需要和 Agent 沟通，省掉大量沟通开销
- 结果：一个人单打独斗的影响力比以往任何时候都大

### 使用编程 Agent 是必选项

- 产品经理：直接做原型验证想法
- 设计师：在代码里迭代，不只是画 Figma
- 工程师：时间从实现转向系统思考

> 不用编程 Agent 的人，会被用的人替代。

### 好的 PM 更好，差的 PM 更差

- **好的产品思维**：做出真正有用的东西，价值更高
- **差的产品思维**：浪费更多资源，产出更多垃圾原型

差的产品想法 + 容易生成的代码 = 更多待评审的垃圾，吞噬大量时间。

### 每个人都需要产品意识

编程 Agent 需要有人告诉它该做什么。知道该让 Agent 做什么（产品意识）成为基本要求。

有产品意识 → 只需简要说明就能理解意图
无产品意识 → 需要超级详细的产品文档

### 专业化的门槛更高了

角色正在融合：
- 设计和产品向来紧密相连
- "设计工程师"（兼具设计和工程）越来越流行

但专业化仍有空间：
- 资深系统架构工程师
- 对客户问题有清晰心智模型的 PM
- 理解用户旅程与交互的设计师

**门槛提高**：不仅要在领域内出类拔萃，还要评审快、沟通强。

### 要么是建设者，要么是评审者

| 角色 | 特点 |
|------|------|
| **建设者** | 有产品思维，能用编程 Agent，有基本设计直觉。可以把功能从想法做到上线。 |
| **评审者** | 需要 EPD 层面的深度评审。门槛高——必须是领域顶尖系统思维者，而且要快。 |

## 核心技能：系统思维

在执行成本极低的世界里，**系统思维**成为真正的差异化能力：

- **工程**：对服务架构、API、数据库的心智模型
- **产品**：对用户真正需要什么的心智模型
- **设计**：对为什么某个东西"用起来就是对"的心智模型

> 做出东西比以往更容易——但不代表做出来的就好。

## 总结

![EPD 角色分布](https://s.baoyu.io/imgs/2026-03-11/coding-agents-reshaping-epd/img-006-HC-9h1ObEAAqqAh.jpg)

每个人都在"建设者-评审者"光谱的某个位置。编程 Agent 让：
- 工程师有更多时间思考产品和设计
- 产品和设计也能写代码了

> 这种人最稀有的版本，站在文化与深度技术的交叉点上。真正的"双语者"——既知道技术上什么是可能的，又能分辨哪些文化潮流是真实的。

**这是一个做建设者的好时代 :)**
