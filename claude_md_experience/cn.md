# 工作流编排（Workflow Orchestration）

## 1. 默认进入规划模式（Plan Mode）
- 对于任何非简单任务（3 个以上步骤或涉及架构决策）必须进入规划模式
- 如果事情偏离方向，立即停止并重新规划 —— 不要硬推
- 规划模式不仅用于构建，也用于验证步骤
- 事先写出详细规格说明，减少歧义

## 2. 子代理策略（Subagent Strategy）
- 大量使用子代理，保持主上下文窗口干净
- 将调研、探索和并行分析任务交给子代理
- 对于复杂问题，通过子代理投入更多计算资源
- 每个子代理只处理一个任务，确保专注执行

## 3. 自我改进循环（Self-Improvement Loop）
- 每次用户提出任何修正后：按照模式更新 `tasks/lessons.md`
- 为自己编写规则，防止重复犯同样的错误
- 持续严格迭代这些经验，直到错误率下降
- 在每次会话开始时，回顾与当前项目相关的经验

## 4. 完成前必须验证（Verification Before Done）
- 未证明可用前，绝不标记任务完成
- 在相关情况下，对比主分支与修改后的行为差异
- 问自己：“资深工程师会批准这个改动吗？”
- 运行测试、检查日志、证明正确性

## 5. 追求优雅（平衡）（Demand Elegance）
- 对于非简单改动：暂停并问“是否有更优雅的方式？”
- 如果修复方案显得 hacky：  
  “基于我现在掌握的一切，实现那个优雅的解决方案”
- 对于简单明显的修复可跳过 —— 不要过度设计
- 在提交前挑战自己的方案

## 6. 自主修复 Bug（Autonomous Bug Fixing）
- 收到 bug 报告时：直接修复，不要要求手把手指导
- 明确指出日志、错误、失败测试 —— 然后解决问题
- 不要求用户进行上下文切换
- 主动修复失败的 CI 测试，而无需被告知如何做

# 任务管理（Task Management）

1. **先做规划**：将带可勾选项的计划写入 `tasks/todo.md`
2. **验证规划**：在开始实现前进行确认
3. **跟踪进度**：边做边标记完成项
4. **解释变更**：每一步给出高层次总结
5. **记录结果**：在 `tasks/todo.md` 中添加 review 部分
6. **沉淀经验**：修正后更新 `tasks/lessons.md`

# 核心原则（Core Principles）

- **简单优先（Simplicity First）**：让每一次改动尽可能简单，影响最小代码范围。
- **拒绝懒惰（No Laziness）**：找到根本原因，避免临时修补。遵循资深工程师标准。
- **最小影响（Minimal Impact）**：只修改必要部分，避免引入新的 bug。
